# Архитектура ttd

Документ описывает, как устроена программа внутри: из каких пакетов состоит,
как проходит одна загрузка и почему приняты те или иные решения.

---

## Общая схема

```
                        ┌─────────────┐
   пользователь ──────► │  cmd/ttd    │  main()
                        └──────┬──────┘
                               │ cli.Main()
                        ┌──────▼──────┐
                        │  internal/  │  разбор аргументов, команды
                        │     cli     │
                        └──┬───┬───┬──┘
                           │   │   │
             ┌─────────────┘   │   └──────────────┐
             ▼                 ▼                  ▼
      ┌────────────┐   ┌────────────┐   ┌────────────┐
      │    tui     │   │    web     │   │  service   │
      └─────┬──────┘   └─────┬──────┘   └─────┬──────┘
            │                │                │
            └────────────────┴────────────────┘
                             ▼
                    ┌──────────────────┐
                    │    engines       │  gallery-dl / yt-dlp / mock
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │    library       │  папки-даты, файлы
                    └──────────────────┘
```

Пакеты `cli`, `tui` и `web` — это три «входа», которые используют один и тот
же движок загрузки (`service` + `engines` + `library`). Логика скачивания нигде
не дублируется.

Код собирается под Linux, macOS и Windows без внешних зависимостей.
Платформенные различия изолированы в нескольких небольших файлах:

| Что | Linux | macOS | Windows |
| --- | --- | --- | --- |
| raw-режим TUI | `term_linux.go` + `term_unix.go` | `term_darwin.go` + `term_unix.go` | `term_windows.go` |
| завершение процесса | `proc_unix.go` (SIGTERM) | `proc_unix.go` (SIGTERM) | `proc_windows.go` (Kill) |
| путь настроек | `~/.config/ttd` | `~/.config/ttd` | `%APPDATA%\ttd` |
| каталог движков | `~/.local/share/ttd` | `~/.local/share/ttd` | `%APPDATA%\ttd` |
| разделитель дат | `|` | `|` | `-` |
| исполняемые файлы | без расширения | без расширения | `.exe` (ищутся и `.cmd`, `.bat`) |

## Пакеты

| Пакет | Ответственность |
| --- | --- |
| `cmd/ttd` | точка входа, вызов `cli.Main()` |
| `internal/cli` | разбор аргументов, подкоманды, печать прогресса |
| `internal/config` | настройки, пути, переменные окружения |
| `internal/model` | общие структуры (`MediaItem`, `JobResult`, `Event`, …) |
| `internal/util` | даты, размеры, запуск процессов, снимки каталогов |
| `internal/engines` | классификация ссылок, команды движков, метаданные, зондирование |
| `internal/service` | оркестрация загрузки: staging → определение дат → раскладка |
| `internal/library` | чтение библиотеки, имена папок-дат |
| `internal/installer` | установка встроенных движков в окружение, диагностика |
| `internal/installer/wheels` | встроенные `.whl`: gallery-dl, yt-dlp и зависимости |
| `internal/tui` | полноэкранный интерфейс, raw-режим терминала |
| `internal/web` | HTTP-сервер и одностраничный интерфейс |
| `internal/version` | версия приложения |

## Жизненный цикл одной загрузки

1. **Разбор аргументов.** `cli` собирает настройки: файл настроек, переменные
   окружения, затем флаги командной строки (флаги важнее всего).

2. **Планирование.** `engines.ExpandURLs` нормализует ссылки
   (`@user` → `https://www.tiktok.com/@user`), определяет вид каждой ссылки и,
   если включены истории, добавляет для профиля вторую ссылку `…/stories`.

3. **Проверка движков.** `installer.EnsureTools` ищет `gallery-dl` и `yt-dlp`
   в кандидатах `config.VenvCandidates()` (явный `TTD_VENV`, `.venv` рядом с
   исходниками, затем `<каталог данных>/venv`) и при необходимости ставит их в
   `config.VenvDir()`. Для установленной копии каталог данных —
   `~/.local/share/ttd` (`TTD_DATA_DIR`), поэтому движки не зависят от места
   бинарника и от наличия исходников.

4. **Выбор движка.** `engines.EngineOrder` задаёт порядок: для историй и
   профилей первым идёт gallery-dl, для одиночных видео — yt-dlp; если движок
   не справился, пробуется следующий.

5. **Загрузка в промежуточный каталог.** Для каждой ссылки создаётся
   `~/ttd/.staging/job-<n>-<время>/`, и движок пишет файлы туда. Так `ttd`
   точно знает, какие файлы появились именно от этой ссылки, и не путает их с
   уже лежащими в библиотеке.

6. **Метаданные.** Движок вызывается с флагами `--write-metadata` (gallery-dl)
   или `--write-info-json` (yt-dlp), поэтому рядом с каждым файлом появляется
   `*.json` с датой публикации.

7. **Раскладка.** `service.place` для каждого файла:
   - читает дату публикации через `engines.ReadPublishDate` (в этом же пакете);
   - если даты нет — берёт дату скачивания;
   - собирает имя папки `<дата скачивания> | <дата публикации>`;
   - переносит файл (`os.Rename`, при необходимости копированием);
   - удаляет служебный `*.json`.

8. **Очистка.** Промежуточный каталог удаляется, файлы метаданных не остаются.

9. **Итог.** `service.Summarize` считает файлы и объём, `cli`/`tui`/`web`
   показывают результат.

## Работа с датами

Имя папки: `19.10.2026 | 17.10.2026` (в Windows — `19.10.2026 - 17.10.2026`,
потому что `|` запрещён в именах файлов).

- `library.Separator` выбирается по `runtime.GOOS`;
- `library.FolderName(download, publish)` собирает имя;
- `library.ParseFolderName` разбирает его обратно и принимает **оба**
  разделителя — библиотеку можно переносить между системами (а также читается
  старый формат из одной даты);
- сортировка библиотеки — по дате скачивания, затем по дате публикации, новые
  сверху.

Откуда берётся дата публикации (`engines/metadata.go`), по порядку проверки:

1. `upload_date` (`YYYYMMDD`) — так пишет yt-dlp;
2. строковые `date` / `published` / `created_at` — так пишет gallery-dl;
3. числовые метки времени в секундах: `timestamp`, `create_time`, …;
4. метки в миллисекундах: `createTime`, `create_time_ms`, … (TikTok отдаёт
   время в миллисекундах).

Если ничего не найдено — используется дата скачивания.

## Движки

Движки описываются интерфейсом `engines.Engine`:

```go
type Engine interface {
    Name() string
    Available() bool
    Version() string
    Download(ctx context.Context, url string, opts model.DownloadOptions,
             dest string, onEvent func(model.Event)) Outcome
}
```

`commandEngine` — общая реализация для внешних процессов: она запускает
команду, построчно читает вывод, разбирает прогресс и отслеживает новые файлы
(через снимок каталога до и после). gallery-dl и yt-dlp отличаются только
сборкой команды и парсером прогресса. `Mock` — отдельная реализация для
демонстрации и тестов.

### Команда gallery-dl

```
gallery-dl --no-colors --config-ignore \
    -D <staging> \
    -f "{user}_{id}{num:?_//>02}.{extension}" \
    --write-metadata \
    [--cookies-from-browser …] [--range 1-N] [--download-archive …] \
    <url>
```

Шаблон имени даёт `user_<id>.mp4` для видео и `user_<id>_01.jpg`,
`user_<id>_02.jpg`, … для слайдшоу.

### Команда yt-dlp

```
yt-dlp --no-colors --newline --no-simulate \
    --print after_move:filepath \
    --write-info-json \
    --progress --progress-template "download:TTD-PROGRESS …" \
    -P <staging> -o "%(uploader,creator,channel,id)s_%(id)s.%(ext)s" \
    -f "bestvideo*+bestaudio/best" --merge-output-format mp4 \
    [--cookies-from-browser …] [--playlist-end N] [--download-archive …] \
    <url>
```

Строка прогресса помечается префиксом `TTD-PROGRESS`, чтобы её было легко
отличить от обычного вывода.

### Установка без интернета

Пакеты движков лежат в `internal/installer/wheels` и встраиваются в бинарник
через `//go:embed wheels/*.whl`. Все колёса — чистый Python (`py3-none-any`),
поэтому один набор подходит для Linux, macOS и Windows.

`installer.Bootstrap`:

1. проверяет Python (нужен 3.10+ — требование yt-dlp);
2. создаёт venv (`python -m venv`), pip берётся из `ensurepip` — без сети;
3. распаковывает встроенные колёса во временный каталог;
4. запускает `pip install --no-index --find-links <каталог> --only-binary=:all:
   gallery-dl yt-dlp`;
5. удаляет временный каталог.

Флаги `ttd install`:

- без флагов — встроенный набор (офлайн);
- `--online` — `pip install --upgrade` с PyPI;
- `--wheels <каталог>` — офлайн-установка из своих колёс.

`installer.BundledVersions()` разбирает имена колёс и показывает версии в
`ttd doctor`.

## События

Всё, что происходит во время загрузки, описывается типом `model.Event`
(по сути `map[string]any`). Виды событий:

| `type` | Смысл |
| --- | --- |
| `start` | начало работы, число ссылок, дата, каталог |
| `job` | начинается обработка ссылки, выбран движок |
| `progress` | процент, скорость, оставшееся время |
| `file` | скачан файл |
| `saved` | файл разложен в папку-дату |
| `result` | итог по ссылке (`ok` / `skipped` / `error` / `cancelled`) |
| `error` | ошибка |
| `install` | строка установки движков |
| `done` | общий итог |

Один и тот же поток событий используют все интерфейсы: `cli` печатает его в
консоль, `tui` рисует на экране, `web` копит в журнале задачи и отдаёт по
`/api/job/<id>`.

## Отмена

Контекст (`context.Context`) протянут от точки входа до процесса движка.
`util.RunStream` при отмене контекста посылает процессу `SIGTERM` и ждёт
завершения (не более 5 секунд). После отмены промежуточный каталог удаляется,
а ссылки помечаются статусом `cancelled`.

---

## Пропуск повторов

Каждому движку передаётся свой файл-архив:

- `~/ttd/.ttd-cache/gallery-dl.archive`
- `~/ttd/.ttd-cache/yt-dlp.archive`

Движок записывает туда идентификаторы скачанного и в следующий раз пропускает
их. Если архив пуст, а в промежуточный каталог ничего не попало — ссылка
получает статус `skipped`. Отключить поведение: `--no-archive`.

## TUI без внешних библиотек

Терминал переводится в raw-режим напрямую через системные вызовы, поэтому у
проекта нет ни одной внешней Go-зависимости:

- **Linux** — `ioctl(TCGETS/TCSETS)` и `syscall.Termios`;
- **macOS** — те же структуры, но `ioctl(TIOCGETA/TIOCSETA)` (BSD-вариант);
- **Windows** — `SetConsoleMode`: отключаются построчный ввод и эхо, включается
  `ENABLE_VIRTUAL_TERMINAL_INPUT/PROCESSING`, вывод переводится в UTF-8; размер
  окна берётся из `GetConsoleScreenBufferInfo`.

Файлы `term_linux.go`, `term_darwin.go`, `term_windows.go` содержат только
платформенные детали, а общая логика — в `term_unix.go`. Клавиши читаются
побайтово, escape-последовательности (F5, F10) распознаются по финальному
байту. Отрисовка — обычные ANSI-последовательности: очистка экрана, вывод
строк, установка курсора.

На платформах, где raw-режим недоступен, включается построчный режим ввода.

## Веб-сервер

`net/http` со стандартным `ServeMux`. `http.ServeFile` даёт поддержку
HTTP `Range` «из коробки» — поэтому видео в браузере можно перематывать.
Доступ к файлам идёт через `util.SafeJoin`, который не позволяет выйти за
пределы библиотеки (проверка `..`).

Задачи хранятся в памяти (`web.Job`): накопленные события и итог. Клиент
опрашивает `/api/job/<id>?since=N` и получает только новые события.

## Тесты

Все тесты работают офлайн:

- `internal/util` — даты, размеры, временные файлы, безопасные пути;
- `internal/library` — имена и разбор папок-дат, сортировка, счётчики;
- `internal/engines` — классификация ссылок, выбор движка, формат качества,
  разбор метаданных о дате публикации;
- `internal/service` — сквозная загрузка через `mock`, раскладка по разным
  датам публикации, обработка совпадения имён;
- `internal/cli` — парсер аргументов;
- `internal/web` — HTTP-эндпоинты, `Range`-запросы и защита от обхода каталога.

Запуск: `go test ./...` или `make test`.

Кросс-компиляция проверяется так:

```bash
GOOS=windows GOARCH=amd64 go build -o ttd.exe ./cmd/ttd
GOOS=darwin  GOARCH=arm64 go build -o ttd-macos ./cmd/ttd
```

## Почему так

- **Go + внешние движки.** Чистый Go-скрейпер TikTok был бы хрупким и не умел
  бы истории и слайдшоу. gallery-dl и yt-dlp уже решают эту задачу и
  обновляются сообществом; Go отвечает за удобный интерфейс, раскладку по
  датам и надёжную оркестрацию.
- **Промежуточный каталог.** Позволяет точно связать файлы с ссылкой и
  определить дату публикации до перемещения в библиотеку.
- **Дата в имени папки, а не в имени файла.** Так вся подборка за один день
  лежит вместе, но при этом видно, какие публикации старые, а какие свежие.
- **Ноль Go-зависимостей.** Бинарник собирается одной командой на любой машине
  без сети и легко переносится.
